# Jason AI 路由分层与上下文收敛设计

日期：2026-03-12

状态：已确认，可进入实施计划

## 目标

让 `jason-kb` 从“默认按基金建议链路处理一切问题”，演进为“按问题类型选择合适上下文与回答模式”。

这次设计同时解决 3 个问题：

- 常识性问题、咨询类问题不再被强行塞入持仓、历史建议和硬校验
- 投资/持仓建议场景不再无限累积历史上下文，降低超时和提示词臃肿风险
- 补齐文档，明确 README 现状，并新增一份给未接触过 `jason-kb` 和 MCP 的朋友使用的远端配置指南

## 当前问题确认

基于对仓库和脚本的检查，当前建议链路有以下特征：

- [scripts/build_temp_input.py](C:\Users\69050\.claude\skills\jason-kb\scripts\build_temp_input.py) 默认围绕持仓/基金事实层构建 `temp_input.json`
- [scripts/call_deepseek.py](C:\Users\69050\.claude\skills\jason-kb\scripts\call_deepseek.py) 默认把 `question + kb_results + financial_profile + market_data + history + 程序计算结果` 一次性拼进提示词
- 只要 `history` 非空，就会整段注入，没有“最近 N 条”“摘要后注入”或“按模式关闭”的逻辑
- 硬校验逻辑默认绑定在当前 DeepSeek 建议链路上，导致普通咨询类问题也难以复用该脚本

这意味着当前系统更像“基金建议生成器”，而不是“人生财务助手”。

## 设计原则

- 保留 `知识库 + last30days + websearch + DeepSeek` 的增强问答能力
- 不把“是否使用持仓/历史/硬校验”设为默认，而是根据问题类型动态决定
- 对投资建议场景保留足够上下文，但把历史建议改成“受控记忆”，而不是原文无限叠加
- 不设置过死的固定条数限制，而是使用弹性上下文预算
- 优先复用现有脚本入口，避免把改动散到过多位置

## 目标架构

建议链路拆成两层：

### 第一层：问题类型路由

系统先判断当前请求属于哪一类：

- `research`
  - 常识问答
  - 原理解释
  - Jason 对某主题的观点咨询
  - 宏观/市场方向咨询
- `advice`
  - 买不买
  - 怎么配
  - 是否调仓
  - 持仓风险
  - 分批计划
- `record`
  - 单纯更新资产、收入、持仓、风险偏好等档案信息
- `history`
  - 明确查看过往建议，不生成新建议

### 第二层：上下文装配

在确定模式后，再决定携带哪些上下文：

- `research`
  - `question`
  - `kb_results`
  - `last30days`
  - `websearch`
- `advice`
  - `question`
  - `kb_results`
  - `last30days`
  - `websearch`
  - `financial_profile`
  - `holdings facts`
  - `compact history`
  - `policy_constraints`
- `record`
  - 不调用 DeepSeek 建议链路
  - 只做资料更新，必要时补一段短提醒
- `history`
  - 直接读建议历史
  - 不走 DeepSeek 建议脚本

## 回答模式设计

### 模式一：Research

适用场景：

- “Jason 怎么看黄金？”
- “现在美股回调怎么看？”
- “基金定投和分批买入有什么区别？”
- “如果只是想了解一个方向值不值得关注”

输入重点：

- Jason 知识库观点
- 近 30 天市场动态
- 补充 web 搜索结果
- 用户问题本身

行为要求：

- 不强行带入个人持仓
- 不带建议历史
- 不启用持仓硬校验
- 输出风格可以是解释、比较、观点整合，不必强行落到“今天买多少”

### 模式二：Advice

适用场景：

- “我这 5 万怎么配？”
- “现在要不要加仓 A 股？”
- “我这只基金是不是太重了？”
- “分几笔买入更合适？”

输入重点：

- Jason 知识库观点
- 近 30 天市场动态
- web 搜索补充
- 财务档案关键字段
- 当前持仓事实层
- 历史建议主线摘要

行为要求：

- 保留现有硬校验，但只在本模式生效
- 继续优先使用结构化事实
- 避免把旧建议中已经完成的动作继续当作当前理由
- 输出要偏行动建议，但允许结合市场和用户风险偏好给出节奏判断

### 模式三：Record

适用场景：

- “我把恒生科技加到 2 万了”
- “我这个月收入涨到 2 万”
- “我把某只基金清了”

行为要求：

- 优先更新档案
- 默认不调用 DeepSeek
- 如果变动重要，可以附一小段提示，但不走完整建议脚本

### 模式四：History

适用场景：

- “之前你给我的建议是什么？”
- “回顾一下最近几次建议”

行为要求：

- 直接读取建议历史
- 不生成新的综合建议

## 上下文预算设计

### 总体原则

上下文控制使用“弹性预算”，而不是写死极小的条数限制。

预算优先级如下：

1. 当前问题
2. 当前最相关的事实
3. 当前最相关的知识库与市场依据
4. 最近仍有约束力的历史主线

### History 策略

`history` 不再全文注入。

改为：

- 优先提取最近几次建议的主线摘要
- 如果最近建议重复度高，则合并成 1 段
- 如果最近存在明显立场变化或策略转折，则保留 2 到 3 段
- 历史内容只保留“仍对当前问题有影响”的部分

例：

- 持续强调“宽基优先、主题小仓、分批执行”时，可以压成一句主线
- 若近期从“减仓恒生科技”转为“维持不动”，则应保留转折说明

### Financial Profile 策略

不默认把完整财务档案原文塞给模型。

优先抽取：

- 风险偏好
- 投资目标
- 流动性要求
- 核心资产结构
- 特殊限制条件

当用户问题明确依赖详细资产结构时，再放宽上下文。

### KB / Market / Web 策略

- `kb_results` 保留最相关的少量片段，不追求把所有检索结果原样拼进去
- `last30days` 保留与问题直接相关的市场动态，并保留日期
- `websearch` 只保留少量高相关事实片段，用于补强 Jason 知识库没有覆盖的部分

### Advice 模式的放宽策略

当问题明显是复杂建议任务时，允许自动扩大上下文预算，例如：

- 结合持仓、市场、Jason 观点做分批计划
- 涉及再平衡、资产配置、节奏判断
- 需要引用当前账户结构与既往策略主线

但即便在 `advice` 模式下，也不能回到“全文拼接”的旧行为。

## 硬校验策略

硬校验只在 `advice` 模式启用。

保留的目标：

- 防止模型编造止损线
- 防止模型捏造仓位比例和金额
- 防止已满足的规则被继续错当成当前动作理由

放宽的目标：

- `research` 模式不启用持仓硬校验
- `advice` 模式只校验与当前建议直接相关的事实
- 历史建议中的旧规则不应自动变成当前硬约束

## 脚本改造方向

### `call_deepseek.py`

当前问题：

- 默认假设所有请求都属于“理财建议”
- 提示词固定带财务档案、历史建议和程序计算结果

目标改造：

- 增加 `mode`
- 按 `mode` 选择 prompt 模板与上下文块
- 把“硬校验”和“结构化事实优先”限定在 `advice` 模式

### `build_temp_input.py`

当前问题：

- 事实层构建偏向持仓建议链路

目标改造：

- 保留现有持仓事实构建能力
- 让脚本支持更轻量的 research 输入结构
- 或者拆出一个单独的上下文组装层，对 `research` 只组装检索内容，对 `advice` 再补持仓事实

### 上下文组装器

建议新增一层专门的上下文组装逻辑，用于：

- 判断模式
- 抽取关键信息
- 生成 `compact history`
- 控制不同模式下的上下文字数

这样可以把“路由”和“DeepSeek 调用”分开，降低后续继续扩展时的耦合。
